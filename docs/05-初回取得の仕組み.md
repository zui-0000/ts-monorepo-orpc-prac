# 初回取得の仕組み

画面を開いたときにデータをどう取るか。**ルーターの `loader` と TanStack Query を
組み合わせる。** 経路そのものの仕組みは
[04-ルーティングの仕組み](./04-ルーティングの仕組み.md) にある。

## loader と画面の両方に書く

**どちらか一方ではない。役割が違う。** `/` の場合はこうなっている。

```ts
// routes/index.tsx —— 描画の前に取り終える
loader: ({ context }) =>
  context.queryClient.query({ ...getUserQueryOption(context.userId), staleTime: "static" }),
```

```ts
// ProfilePage.tsx —— 取れているものを購読する
const { data: user } = useSuspenseQuery(getUserQueryOption(userId));
```

`loader` がキャッシュを温め、画面はそれを読む。**同じ `queryOptions` を指すため通信は
1 回で済む。**

画面だけで取ると 3 つを失う。

| 失うもの         | 何が起きるか                                                      |
| ---------------- | ----------------------------------------------------------------- |
| 先読み           | `defaultPreload: "intent"` が効かない。リンクに触れても始まらない |
| 待ち時間の直列化 | 描画してから取りに行くため、`beforeLoad` の取得と直列になる       |
| 読み込み表示     | 毎回 `Suspense` に落ちる。`PageLoadingSpinner` が都度出る         |

**`loader` だけでも足りない。** 取ったものを画面が購読しないと、更新後の再取得に
追従できない (後述)。

## 複数を取る

`loader` はただの非同期関数なので、いくつ呼んでもよい。**依存が無いものは
`Promise.all` で束ねる。**

```ts
loader: async ({ context }) => {
  await Promise.all([
    context.queryClient.query({ ...getUserQueryOption(context.userId), staleTime: "static" }),
    context.queryClient.query({ ...getPostsQueryOption(context.userId), staleTime: "static" }),
  ]);
},
```

`await` を 2 行並べると直列になり、1 本目が返るまで 2 本目が始まらない。

**依存があるなら直列にするしかない。** `/` が既にその形である。

```txt
beforeLoad  セッションを取る        → userId が判明
loader      その userId で利用者を取る
```

`userId` が無ければ 2 本目を投げられない。**並列にできないのではなく、してはいけない。**

**親子の経路は並列に走る。** ルーターのライフサイクルで読み込み段階は並列と定められて
いるため、共通の取得を親へ寄せても遅くならない。

## async は本体で await するときだけ

`loader` は Promise を返せばよい。**返した Promise をルーターが待つため、`async` を
付けなくても動く。** 型定義の戻り値は `any` である。

```ts
type RouteLoaderFn<...> = (match: LoaderFnContext<...>) => any;
```

`loaderData` の型も変わらない。`ResolveLoaderData` が `LooseAsyncReturnType` で
Promise を剥がすためである。**付けると Promise を二重に包むだけ**になる。

`/` の 2 つがそのまま使い分けの例になっている。

```ts
// loader —— 取ったものをそのまま渡す。途中で待つ場所が無いので async は不要
loader: ({ context }) =>
  context.queryClient.query({ ...getUserQueryOption(context.userId), staleTime: "static" }),

// beforeLoad —— 結果を見て分岐し、別の値を返す。await が要るので async
beforeLoad: async ({ context }) => {
  const session = await context.queryClient.query({ ...getSessionQueryOption, staleTime: "static" });
  if (!session) throw redirect({ to: "/sign-in" });
  return { userId: session.user.id };
},
```

上の `Promise.all` も、束ねて返すだけなら `async` は要らない。

```ts
loader: ({ context }) => Promise.all([...]),
```

## 検索パラメータで取る内容が変わるとき

`loaderDeps` に依存を書く。**使うものだけ返すこと。**

```ts
loaderDeps: ({ search }) => ({ page: search.page }),
loader: ({ context, deps }) => context.queryClient.query(getPostsQueryOption(deps.page)),
```

`search` を丸ごと返すと、`loader` が使っていないパラメータが変わっただけで再読み込みが
走る。`sign-in.tsx` の `registered` は `loader` で使っていないため書いていない。

## staleTime を 3 つ使い分けている

| 場所                    | 値         | 意図                                                 |
| ----------------------- | ---------- | ---------------------------------------------------- |
| `QueryClient` の既定    | `0`        | 取ったものを即座に古い扱いにする。保持は各所が決める |
| `getSessionQueryOption` | `30_000`   | セッションは 30 秒使い回す。経路ごとに問い合わせない |
| `loader` の呼び出し     | `"static"` | あれば使い、無ければ取る。`ensureQueryData` の後継   |

**`loader` の `"static"` が効くのは初回だけではない。** 既に取れていれば通信せずに
通過するため、戻る操作や先読みで温まった経路は即座に描ける。

## ローディングの出し分け

**2 つの仕組みがあり、出る場面が違う。**

|                    | いつ出るか                         | どこに書くか                 |
| ------------------ | ---------------------------------- | ---------------------------- |
| `pendingComponent` | ルートの `loader` が走っている間   | ルート、またはルーターの既定 |
| `<Suspense>`       | 画面の `useSuspenseQuery` が中断中 | `RootLayout`                 |

**両方要る。** `loader` で先読みした経路は `useSuspenseQuery` が中断しないため
`pendingComponent` が受け持ち、先読みしていない取得は `<Suspense>` が受け持つ。

出し分けは 2 段である。ルートに書いてあればそれ、無ければルーターの既定が使われる。

```ts
// App.tsx —— アプリ共通
createRouter({ routeTree, defaultPendingComponent: PageLoadingSpinner, ... });
```

```ts
// 経路ごとに変えたいとき
export const Route = createFileRoute("/user/edit")({
  pendingComponent: EditFormSkeleton,
  loader: ...,
});
```

**`component` に被せる必要は無い。** ルーターが `loader` の実行中に自分で描く。

### 遅延の既定値は触って決める

**すぐには出ない。** 2 つのノブがある。

| 設定                  | 既定 | 意味                                               |
| --------------------- | ---- | -------------------------------------------------- |
| `defaultPendingMs`    | 1000 | これを超えて初めて表示する。速い遷移で点滅させない |
| `defaultPendingMinMs` | 500  | 一度出したら最低これだけ保つ。パッと消えるのを防ぐ |

**この 2 つは机上で決めない。** 1 秒以内に終わる遷移では何も出ないため、「設定したのに
出ない」と誤解しやすい。**実際に動かして、遅く感じるか、チラついて鬱陶しいかで決める。**

試すにはモックに遅延を入れる。

```ts
import { delay, http } from "msw";

http.get("/api/users/:id", async ({ params }) => {
  await delay(1500);
  return getUser(String(params.id));
});
```

`defaultPendingMs` を下げれば出やすく、上げれば出にくくなる。**速い環境だけで決めると
遅い環境で何も出ないまま待たせる**ため、遅延を変えて両側を見ること。

## 取り直す

更新したら**キーを無効化する。** 画面が `useSuspenseQuery` で購読しているため、無効化が
そのまま再取得と再描画になる。

```ts
// ProfilePage.tsx
const update = useUpdateProfileMutation({
  onSuccess: () =>
    queryClient.invalidateQueries({
      queryKey: CONTEXT_KEYS.USER_CONTEXT_KEY.get(userId),
    }),
});
```

**ここが「`loader` だけでは足りない」理由である。** `loader` は経路に入るときしか走らな
いため、画面に留まったままの更新には反応しない。
