# ADR (Architecture Decision Records)

このプロジェクトの意思決定を記録する場所。

**「なぜこうなっているのか」を後から再構築できるようにする**のが目的であり、
アーキテクチャに限らずライブラリ選定や運用ルールの決定も対象とする。
決定そのものより、**却下した選択肢とその理由**に価値がある。

## フォーマット

**MADR 4.0.0** に準拠する。

```txt
---
status: {proposed | rejected | accepted | deprecated | superseded by ...}
date: {YYYY-MM-DD}
decision-makers: {決定した人}
consulted: {意見を求めた相手（双方向のやりとりがあった人）}
informed: {結果を共有する相手（一方向）}
---

# {解決した問題と採用した解決策を表す短いタイトル}

## 背景と課題 (Context and Problem Statement)
## 決定要因 (Decision Drivers)
## 検討した選択肢 (Considered Options)
## 決定 (Decision Outcome)
### 結果 (Consequences)
### 確認方法 (Confirmation)
## 各選択肢の評価 (Pros and Cons of the Options)
## 補足情報 (More Information)
```

各セクションの書き方は既存の ADR を参照。特に以下の 2 つは形式が決まっている。

**結果 (Consequences)** — 良い点と悪い点を箇条書きで並べる。

```markdown
* Good, because {良い結果}
* Bad, because {悪い結果・トレードオフ}
```

**各選択肢の評価 (Pros and Cons of the Options)** — 選択肢ごとに見出しを作り、
`Good` / `Neutral` / `Bad` で評価する。**採用しなかった案こそ丁寧に書く。**

## 運用ルール

### ディレクトリ構成

```txt
docs/adr/
├── README.md          ← このファイル（索引）
├── ライブラリ関連/
│   ├── ADR-01-....md
│   └── ADR-02-....md
├── 命名関連/
│   └── ADR-01-....md
├── 設計関連/
│   └── ADR-01-....md
├── {カテゴリ名}/
└── 未分類/            ← 分類に迷ったらここ（無ければ作る）
```

- **サブフォルダは 1 階層のみ。ネストしない**
- **番号はカテゴリ内でローカルに連番**（グローバル一意ではない）
- 分類に迷ったら `未分類/` に置く。**書かないより置く方がよい**。
  後から適切なカテゴリへ移動する

この方式は MADR 公式が
[0010-support-categories](https://github.com/adr/madr/blob/main/docs/decisions/0010-support-categories.md)
で 7 案を比較した結果、採用している構成と同じ。
公式も「ADR を一意に識別する番号が無い」ことを欠点として認めた上で、
フォルダによるグルーピングの利点を優先している。

### ファイル名

```txt
ADR-{NN}-{タイトル}.md
```

- タイトルは**本文の `#` 見出しと揃える**
- 「〜する理由」のような語尾は付けない。理由を書くのが ADR なので冗長
- 日本語のファイル名を使うため、git の設定を入れておくこと

  ```bash
  git config core.quotepath false
  ```

  入れないと `git status` で `\343\203\251...` とエスケープ表示される。

### 相互参照

- **同一カテゴリ内**: `ADR-02` と書く
- **カテゴリを跨ぐ**: `ライブラリ関連/ADR-02` のようにカテゴリ名を含める

カテゴリごとのローカル番号を採用しているため、
番号だけでは一意に定まらない点に注意する。

### ステータスの更新

決定が覆ったら、古い ADR を**消さずに** `status` を書き換える。

| 値                                    | 意味                    |
| ------------------------------------- | ----------------------- |
| `proposed`                            | 提案中                  |
| `accepted`                            | 採用中                  |
| `rejected`                            | 却下した                |
| `deprecated`                          | 使わなくなった          |
| `superseded by ライブラリ関連/ADR-05` | 別の ADR に置き換わった |

**「なぜ前はそうしていたのか」も再構築の材料**になるため、履歴を残す。
新しい ADR 側には、何を覆したのかを書く。

### 書く粒度

- 迷った末に決めたこと、**却下した案があること**は書く
- 自明なこと、後から誰でも同じ結論に至ることは書かなくてよい
- **完璧なフォーマットを整えるより、1 つ書く方が価値がある**。
  埋められないセクションは空のままでも構わない

### コードブロック

**言語を必ず指定する** (`docs/` 全体に適用)。指定が無いと描画側が中身から
言語を推測するため、ディレクトリツリーが差分として色付けされるなど、
**読む場所によって見え方が変わる。**

| 内容                                         | 指定                         |
| -------------------------------------------- | ---------------------------- |
| コード                                       | `ts` / `json` / `jsonc` など |
| シェルで打った実測 (`$ ` から始まる行を含む) | `zsh`                        |
| ディレクトリツリー、ログ、コマンド出力、雛形 | `txt`                        |

迷ったら `txt`。色を付けたいものだけ言語を名乗る。
