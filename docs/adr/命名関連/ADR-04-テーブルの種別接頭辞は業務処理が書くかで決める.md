# テーブルの種別接頭辞は業務処理が書くかで決める

## 背景と課題 (Context and Problem Statement)

最初のテーブルを作った時点から `t_user` という名前を使っていたが、
**接頭辞が何を意味するのかも、どう判定するのかも文書化していなかった。**
ADR-03 は「テーブル名 (`t_` 接頭辞) や列名の規約は別途決めたもの」と参照しているが、
**その実体はどこにも無い。**

better-auth の配線で 3 テーブル (`t_session` / `t_account` / `t_verification`) が
増えるにあたり、それぞれにどの接頭辞を付けるかを決める必要が生じた。

### 判定基準が割れることが実際に起きた

同じ 4 テーブルに対して、**2 つの基準が別の答えを出した。**

| 基準                                | `user` | `session` | `account` | `verification` |
| ----------------------------------- | ------ | --------- | --------- | -------------- |
| **業務処理が行を書くか** (採用)     | `t_`   | `t_`      | `t_`      | `t_`           |
| 他のテーブルから参照されるか (却下) | `m_`   | `t_`      | `m_`      | `t_`           |

後者は「マスタデータとは業務活動が参照する前提データである」という定義から、
外部キーの向きで判定する。`t_session.user_id` と `t_account.user_id` が
`user` を参照しているため、`user` はマスタ側になる。

**接頭辞の一覧だけを決めても、判定基準が無ければテーブルが増えるたびに同じ議論が起きる。**
本 ADR が決めるのは接頭辞そのものより**判定基準**である。

## 決定要因 (Decision Drivers)

- **判定が一意に定まること。** 人によって答えが変わらない
- **運用上の扱いと一致すること。** バックアップ、テストデータ、件数の見積もり
- 予約語との衝突を避けられること
- 名前を見て種別が分かること

## 検討した選択肢 (Considered Options)

- 種別接頭辞 + 「業務処理が行を書くか」で判定
- 種別接頭辞 + 「他のテーブルから参照されるか」で判定
- 接頭辞を付けない (素の `users` / `sessions`)
- 一律 `t_` (種別を区別せず、衝突回避だけを目的にする)

## 決定 (Decision Outcome)

**「種別接頭辞を全テーブルに一律で付け、判定は『業務処理が行を書くか』で行う」を採用する。**

| 接頭辞 | 種別               | 判定                                   | 中身の所有者                |
| ------ | ------------------ | -------------------------------------- | --------------------------- |
| `t_`   | トランザクション系 | **業務処理が行を挿入・更新する**       | アプリケーション            |
| `m_`   | マスタ系           | **業務処理では更新されない**参照データ | マイグレーション / 管理操作 |
| `c_`   | キャッシュ系       | 再生成できる派生データ                 | 生成処理                    |

**テーブル名は単数形とする** (`t_user` であって `t_users` ではない)。

### 判定は「誰が書くか」で行う

**「データモデル上どういう役割か」ではなく「中身がどこから来るか」で切る。**
この基準を採ったのは、**運用の単位と一致するため**である。

- `m_` はマイグレーションや seed が所有する。**テストデータに含める必要があり、
  件数は設計時に決まり、バックアップの重要度が違う**
- `t_` はアプリケーションが所有する。**利用に比例して増え、
  テストでは毎回作り直す**

「他から参照されるか」で切ると、この運用上の差と一致しない。`t_user` は
参照される側だが、中身はサインアップ処理が作るため `m_` の扱い
(seed で用意する、件数が決まっている) は当てはまらない。

### 本スキーマへの適用

better-auth の 4 テーブルは**すべて業務処理が行を書く**ため、一律 `t_` になる。

```txt
t_user           サインアップ処理が行を挿入する
t_session        サインイン処理が行を挿入し、期限切れで消える
t_account        サインアップ / アカウント連携処理が行を挿入する
t_verification   メール検証・パスワードリセットの発行処理が行を挿入する
```

`m_` に該当するテーブルは現時点で存在しない。

### 列名は snake_case とし、中身が読める名前にする

SQL の列名は snake_case とする。**drizzle の TS プロパティ名は better-auth の既定に
固定されるが、SQL 名は自由**なので、中身が読める名前を付ける。

| TS 名 (変更不可) | SQL 名                | なぜ変えたか                                                                 |
| ---------------- | --------------------- | ---------------------------------------------------------------------------- |
| `emailVerified`  | `is_email_verified`   | **真偽値には `is_` を付ける。** `WHERE is_email_verified` が述語として読める |
| `image`          | `image_url`           | 常に URL。実体 (`bytea`) と誤読される                                        |
| `password`       | `password_hash`       | 常に argon2id のハッシュ。**平文と誤読されるのは危険側のズレ**               |
| `accountId`      | `provider_account_id` | `t_account.id` と紛らわしい。実際は発行者側の識別子 (Google の `sub`)        |

`has_` / `can_` といった他の述語接頭辞は現時点では決めていない。

**中身が用途で変わる列は汎用名のままにする。** `t_verification.identifier` は
`reset-password:<token>` や `delete-account-<token>` を、`value` はパスワード
リセットならユーザー ID を持つ。**多相なので具体的に名付けると嘘になる。**
名前ではなくコメントで補う。

**TS 名と SQL 名のズレは drizzle の列定義に留める。** better-auth の `fields` で
TS 名のほうを写す案もあるが、better-auth の API は既定名 (`user.emailVerified`) を
返すため **TS 側に名前が 2 つできる**。drizzle の列定義は SQL 名と TS 名を並べて
宣言する場所であり、対応表としてはここ 1 つで足りる。

```ts
emailVerified: boolean("is_email_verified").notNull().default(false);
//  ↑ better-auth の既定 (変更不可)          ↑ SQL 名は自由
```

### drizzle の変数名は SQL 名をキャメル化する

```ts
export const tUser = pgTable("t_user", { ... });
```

**接頭辞ごとキャメル化する** (`t_user` → `tUser`)。理由は 2 つ。

- **SQL からの逆引きが機械的になる。** マイグレーションの SQL で `t_account` を
  見つけたら `tAccount` を grep すれば必ず当たる。ADR-03 のとおり、SQL 側の名前を
  アプリが文字列で持つ場面は実在する
- **ドメインの語彙と衝突しない。** `import { tUser }` と `import type { User }` が
  同じファイルに並んでも視覚的に混ざらない (`user-repository.ts` が実際にそう)

drizzle 公式の例は複数形・接頭辞なし (`users`) だが、SQL 名との対応が崩れるため採らない。
**テーブルオブジェクトは値なので lowerCamel** である (型を生む `UserSchema` は Pascal)。

### 結果 (Consequences)

- Good, because **判定が一意に定まる。** 「その行は業務処理が作るか」は
  yes / no で答えられ、人によってブレない
- Good, because **運用の単位と名前が一致する。** `m_` を見たら
  「seed が持つ、テストに含める、件数が決まっている」と読める
- Good, because **予約語を避けられる。** `user` は Postgres の予約語で、
  素の `CREATE TABLE user` は構文エラーになる (実測)
- Good, because 種別が名前で分かり、`\dt` の一覧がグルーピングされる
- Bad, because **分類が変わると改名が連鎖する。** テーブル名は外部キー名・索引名・
  アプリが持つ文字列すべてに波及する。「マスタだと思っていたが違った」の修正コストが高い
- Bad, because 接頭辞の意味を知らない人には読めない。本 ADR がその答えになる
- Neutral, because 素の名前より 2 文字長い

### 確認方法 (Confirmation)

**機械的な検査は用意していない。** テーブルを足すときに本 ADR の判定を当てること。

予約語との衝突は実測した (PostgreSQL 18.4)。

```zsh
$ psql -c 'CREATE TABLE user (id int);'
ERROR:  syntax error at or near "user"
$ psql -c 'CREATE TABLE session (id int);'
CREATE TABLE
```

**`user` だけが予約語**であり、`session` / `account` / `verification` は素で作れる。
つまり衝突回避だけが目的なら接頭辞は 1 テーブルにしか要らない。
**一律で付けるのは一貫性のため**である。

## 各選択肢の評価 (Pros and Cons of the Options)

### 種別接頭辞 + 「業務処理が行を書くか」で判定 (採用)

- Good, because 判定が yes / no で決まり、人によってブレない
- Good, because 運用 (seed・テストデータ・バックアップ・件数見積もり) と一致する
- Neutral, because データモデル上の役割 (参照される / する) は名前に出ない
- Bad, because 分類が変わると改名が連鎖する

### 種別接頭辞 + 「他のテーブルから参照されるか」で判定

「マスタデータとは業務活動が参照する前提データ」という古典的な定義に忠実な案。

- Good, because **定義に忠実。** 外部キーの向きという客観的な事実で判定でき、
  スキーマを見れば機械的に決まる
- Good, because 日本の SIer 文化の「顧客マスタ」「社員マスタ」と一致する。
  その出身者には自然
- Bad, because **運用上の扱いと食い違う。** `t_user` は参照される側だが、
  中身はサインアップ処理が作る。seed で用意するものではない
- Bad, because **後から変わる。** 今は誰にも参照されていないテーブルが、
  参照されるようになった時点で分類が変わり、改名が要る

### 接頭辞を付けない (素の `users` / `sessions`)

- Good, because 短い。drizzle・Rails・Prisma などの流儀と一致する
- Good, because **分類が変わっても改名が要らない。** 名前に分類を載せないため、
  接頭辞方式の最大の欠点が最初から存在しない
- Bad, because **`user` が予約語**なので、そこだけ引用符か別名が要る。
  1 テーブルだけ例外になる
- Bad, because 種別が名前から読めない。`\dt` の一覧がグルーピングされない
- Neutral, because 近年はこちらが増えている。**「分類は不安定なのに名前で固定する」
  という批判**は正当であり、本 ADR もそれを Bad として認めている

### 一律 `t_` (種別を区別しない)

- Good, because 判定が不要。迷う場面が消える
- Good, because 予約語を避けられる
- Bad, because **接頭辞が情報を持たない。** 全部同じなら区別の役に立たず、
  2 文字を払って何も得ていない

## 補足情報 (More Information)

### better-auth のテーブルを足すときの判定

プラグインを足すとテーブルが増える。判定は同じく「業務処理が行を書くか」。

| better-auth のテーブル | 判定 | 理由                                           |
| ---------------------- | ---- | ---------------------------------------------- |
| `rateLimit`            | `c_` | 再生成できる派生データ。消えても業務は壊れない |
| `organization` など    | `t_` | 業務処理が作る                                 |

`rateLimit` は `rateLimit.storage: "database"` を指定したときだけ現れる
(既定はメモリ)。現時点では作っていない。

### この判定基準を選んだ経緯

本 ADR の「背景と課題」に書いたとおり、**同じ 4 テーブルに 2 つの基準が
別の答えを出した**のがきっかけである。片方は `t_user`、もう片方は `m_user` を出した。

**接頭辞の一覧 (`t_` / `m_` / `c_`) だけを決めても不十分**で、
判定基準を書かなければ次に迷う。ここが本 ADR の中心である。

### 命名の対象範囲

この ADR が扱うのは**テーブル名の接頭辞・単複、列名、drizzle の変数名**である。

- 索引名・制約名は ADR-03 が扱う
- ファイル名は ADR-01 が扱う
