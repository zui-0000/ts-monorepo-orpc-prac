# メール検証の仕組み

**送信サービスを決めないまま検証フローを成立させている。** その形と、開発時にどう
確かめるかを記録する。学習用のリポジトリなので送信手段は保留しているが、
**保留したまま動く形**にしてある。

## なぜ検証するのか

`requireEmailVerification: true` にしている。**未検証のアカウントではサインインさせない。**

塞いでいるのは**未検証アカウントの先取り**である。攻撃者が他人のメールアドレスで
先に登録しておき、本人が後から来たときにそのアカウントを乗っ取る手口で、
検証を挟まないと「登録できた側」が持ち主になってしまう。

## 送信手段を決めずに成立する理由

better-auth が求めるのは **`{ user, url, token }` を受け取る関数**だけである。
**メールを送る義務は無い。** 検証 URL がどこかに出れば検証は成立する。

```ts
// contexts/auth/infrastructure/send-verification-email.ts
export const sendVerificationEmail = async ({ user, url }) => {
  console.info(`宛先: ${user.email}\nリンク: ${url}`);
};
```

**ここが差し替え口。** 本番では中身を送信サービスの呼び出しに替える。
**URL の組み立ては better-auth が済ませている**ので、替えるのは「どう届けるか」だけ。

### この関数は必須である

`requireEmailVerification: true` にして `sendVerificationEmail` を置かないと、
**誰もログインできなくなる。** better-auth はサインインを 403 で止めたまま、
検証する手段を出さない。

```js
// better-auth/dist/api/routes/sign-in.mjs
if (options?.emailAndPassword?.requireEmailVerification && !user.emailVerified) {
  if (!options?.emailVerification?.sendVerificationEmail)
    throw APIError.from("FORBIDDEN", BASE_ERROR_CODES.EMAIL_NOT_VERIFIED);
  ...
}
```

## 設定

```ts
emailVerification: {
  sendVerificationEmail,          // 上の関数
  sendOnSignUp: true,             // サインアップ直後に出す
  sendOnSignIn: true,             // 未検証のままサインインを試みたら再発行する
  autoSignInAfterVerification: true, // 検証を終えたらそのままサインイン状態に
},
emailAndPassword: {
  requireEmailVerification: true,
},
```

`sendOnSignIn: true` が開発で効く。**コンソールを流してリンクを見失っても、
サインインし直せばまた出る。** 既定は `false` で、そのままだと再発行の手段が
`/api/auth/send-verification-email` を自分で叩くことになる。

トークンの寿命は既定の 1 時間 (`expiresIn`)。

## 開発時の手順

```zsh
$ bun --env-file=.env src/main.ts

# 1. サインアップする
$ curl -s -X POST http://localhost:3000/api/auth/sign-up/email \
    -H 'content-type: application/json' \
    -d '{"name":"検証太郎","email":"verify@example.com","password":"correct-horse-battery-staple-15"}'
{"token":null,"user":{...,"emailVerified":false,...}}
```

**`token` が `null`** で返る。検証が済むまでセッションは張られない。

サーバのコンソールにリンクが出る。

```txt
──────── メール検証 ────────
宛先: verify@example.com
リンク: http://localhost:3000/api/auth/verify-email?token=eyJhbGciOi...&callbackURL=%2F
────────────────────────────
```

```zsh
# 2. この時点でサインインは通らない
$ curl -s -X POST http://localhost:3000/api/auth/sign-in/email ...
{"message":"Email not verified","code":"EMAIL_NOT_VERIFIED"}   # 403

# 3. リンクを開く (ブラウザでも curl -L でもよい)
$ curl -s -L -c cookie.txt "http://localhost:3000/api/auth/verify-email?token=..."

# 4. 検証済みになり、サインインできる
$ psql -c 'SELECT is_email_verified FROM auth.t_user;'
 t
$ curl -s -X POST http://localhost:3000/api/auth/sign-in/email ...   # 200
```

### リンクを踏むと 404 が返るが、失敗ではない

better-auth は検証を終えたあと `callbackURL` (既定は `/`) へリダイレクトする。
**API サーバにその画面が無いため 404 になるだけ**で、検証そのものは成功している。
`is_email_verified` が `t` になっていることで確かめられる。フロントエンドを用意すれば
リダイレクト先が実在するようになる。

## トークンはどこにあるか

**`t_verification` テーブルには入らない。** メール検証のトークンは JWT で、
`BETTER_AUTH_SECRET` で署名して URL に載せている。`t_verification` を使うのは
パスワードリセットや OAuth の state など別の用途である
(`shared/infrastructure/db/schema/auth/t-verification.ts` の表を参照)。

そのため**検証リンクは DB を見ても分からない。** 失くしたら再発行する
(`sendOnSignIn: true` があるのでサインインし直せばよい)。

## 本番で決めること

保留にしているのは**届け方**だけである。決めるときに触るのは
`send-verification-email.ts` の中身のみ。

- 送信サービス (Resend / SES / SendGrid など)
- メールの文面と `from` アドレス
- 送信の失敗をどう扱うか (現在の実装は失敗しない)
- **URL をログに出さないこと。** トークンがそのまま入っているため、
  本番のログに残すと検証リンクを盗めてしまう

開発でコンソールに出しているのは、届ける先が他に無いからである。
